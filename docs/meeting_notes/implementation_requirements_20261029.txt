一、他们明确表达的目标和要求

1. 为目标包用户增加可使用的估计方法。
Ed在15:20:13问代码能否构成“a meaningful pull request for that package”；15:23:45—15:25:17强调已经使用Cuthbert的用户需要能在Cuthbert中使用IFAD，并判断是否接纳扩展。
据此，应明确用户原来能做什么，扩展后多了什么，以及用户怎样调用。完成同一种语言下的实现，或仅把代码放进该包目录，不能充分说明对目标包的贡献。

2. 真正利用目标包的PF和接口。
Ed在15:20:40—15:21:40追问IF2/IFAD究竟调用了Cuthbert的什么；15:25:47质疑把PyPOMP代码放进Cuthbert目录是否足以算Cuthbert实现。
15:27:20明确认可按该包的框架、语言和写法实现。
据此，需从实际函数调用说明原有初始化、传播、权重、重采样和滤波循环分别如何保留，新增代码在哪一步加入。只使用JAX/PyTorch、通用优化器或一个训练接口，不能自动视为使用了该包的粒子滤波。

3. IF2的参数扰动应封装成可复用功能。
15:27:43—15:28:08讨论随机游走可以通过模型修改和现有PF实现；15:28:52 Ed强调不希望每个模型都需要单独改造，Giles认可。
据此，模型提供正常的状态与观测计算及参数接口；参数粒子、扰动和IF2过程应由通用扩展负责，而不是在每个模型脚本中分别重写。
这是对实现组织方式的要求，不表示接入任意模型都不需要模型适配，也不要求支持包中所有模型或所有滤波器。

4. 对已有ADPF的包，从其ADPF机制出发增加DMOP折扣。
Ed在15:28:22—15:28:34以Cuthbert为例说已有ADPF，DMOP是对它增加alpha的较小改动；Giles在15:28:42指出这是内部改变，因而可能适合PR。
据此，应定位原有权重和导数计算，再解释折扣究竟修改什么。不能把我们新写的alpha=1实现未经区分地称作该包原来的ADPF。
这个要求针对相应已有机制，不能推成所有包都有ADPF，或所有包都必须用同一公式和代码布局。

5. 从原代码出发做必要改动，提供容易理解的diff。
Giles在15:29:17说“take their code and make the minimal change”；15:29:41提出“diff with their code”，15:29:54要求“a fairly intelligible diff”。
据此，要能看清保留了什么、改动了什么、每处为什么必要。算法改动、运行支持、测试与文档应分清。
没有规定新增行数上限；没有规定必须直接修改particle_filter.py。若包已有适当的回调或装饰器接口，通过它扩展也可以符合方向。

6. 选择有意义的比较，并限制扩展范围。
15:24:45—15:25:17强调同一包内不同方法对包用户的意义；15:53:37—15:53:55肯定原方法、原方法加IF2、我们的方法这种展示。
15:47:51—15:50:30质疑PF加Nelder-Mead是否代表该包常用做法；15:52:23 Giles询问CPU包未做IF2究竟是架构限制还是没有实现。
15:56:28—15:56:46 Giles要求先规定IF2/IFAD移植到什么程度，避免无限深入。
据此，先核对原有方法与接口。哪些包适合IF2、哪些能进一步支持DMOP/IFAD，要逐包决定；不为表格整齐强行补齐所有方法。

7. 准备短报告和代码，再开始与维护者交流。
15:30:43—15:31:05和15:54:46—15:57:33支持先提供报告、代码和结果，询问维护者是否对PR感兴趣。
15:57:16强调结果是交流的起点。
这里要求的是可解释、可复现、可供审查的实现，不表示必须先做到上游已经合并，更不授权本助手自行发邮件或创建PR。

二、会议没有明确规定的事情

- 没有规定必须使用同一套Adam、同一个函数名、同一个文件结构或完全相同的公共API。
- 没有规定实验驱动必须直接调用一个包级fit完成全部步骤；计时停止、恢复、批处理和论文设置可以需要驱动代码。关键是这些代码是否合理复用和清楚表达新增算法。
- “让通用fit和实验驱动共用单步函数”是本助手提出的重构建议。是否需要采用，应在审查重复内容、行为差异和接口适配后决定，不能冒充Ed/Giles的硬性要求。
- 没有规定所有包都必须加入IF2和IFAD，或必须给每个包提交PR。
- 固定随机数的Nelder-Mead属于现场探索性讨论，不是确定的统一方案。
- 没有要求为了上述实现审查重跑Cuthbert A/B/C。其既有Dacca结果应保留，并准确对应实际运行的代码。
- 没有把“有实验结果”“测试全过”“文件来源hash一致”单独当作实现已符合要求的充分证明。

三、据此采用的逐包工作步骤（我们的执行办法）

当前只处理Cuthbert。完成本包的以下材料，再选择下一包；不同时重构多个包。

步骤1：说明原包。
固定源码版本，列出原PF/ADPF调用流程、模型接口、参数估计接口和返回状态。区分包已有方法与外部优化器。

步骤2：写清拟增加的能力。
分别说明IF2增加什么、DMOP修改哪里、IFAD如何组合两阶段；明确适用模型与不支持的接口。先确定方案，不以写出更多代码为目标。

步骤3：对照现有实现。
逐处标明原包函数、原函数修改和新增函数，检查是否真正复用原有计算。
对重复实现逐一判断：必要的协议/运行差异，还是可以共用的算法代码。不能仅凭函数名不同就要求重构。

步骤4：只修明确的问题。
在独立开发代码中做必要修改，并记录为什么。已有冻结实验源与结果不改。若代码本来符合要求，直接整理证据与diff，不为“最小修改”强行重写。

步骤5：做与改动对应的实现检查。
检查原行为是否保留、扰动与重采样是否正确衔接、梯度修改是否符合预期、模型能否通过统一接口使用新增功能。
已有测试可复用；发生重构时再做有针对性的前后核对。重构若确实改变数值行为，应明确记录，不能自动声称旧实验验证了新代码。
这些是为验证实现而制定的工程步骤，不是会议逐项规定的测试列表，也不是新增大规模估计实验。

步骤6：交付本包的审查材料。
一份原包调用与修改对照；一份包含新增文件的完整diff；一个实际执行拟交付接口的例子；相应测试记录；现有实验调用与该实现的对应说明。
逐项给出“已做到”“需要修改”“需维护者讨论”，随后再处理下一包。
